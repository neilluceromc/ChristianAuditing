1Inventory v2 — foundations, primitives and five screens
1aReasoning, tokens and the status system
How I read the brief

A back-office tool earns its keep in the peripheral vision.

Nobody reads these screens. They scan them, hundreds of times a day, looking for one row. So the design work is almost entirely about making state legible without reading — position, weight, and a single hue family per meaning — and about never moving anything after load.

The primitive layer is the deliverable. 39 routes hand-rolling their own controls is why it feels clunky; one Button with four variants fixes more perceived quality than any new screen would.

Assumptions I made
Server contract untouched — every control here maps to an existing action or a query param.
Saved-filter nav stays, but becomes a mirror of in-page filter state rather than a separate concept (compared in 1h).
Density toggle changes row height and nothing else — no font-size change, so column widths never shift.
Every lifecycle mutation routes through Approvals, so most "write" UI is really "request" UI. I labelled buttons accordingly.
